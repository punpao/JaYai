## 1. ภาพรวมผลิตภัณฑ์

### ปัญหาที่แก้

คนไทยส่วนใหญ่ไม่รู้ว่าข้อมูลส่วนบุคคลของตัวเองอยู่ในมือใครบ้าง และถึงจะรู้ว่ามีสิทธิ์ตาม PDPA ก็ไม่รู้จะเริ่มใช้สิทธิ์ยังไง ปัญหาแยกได้เป็น 3 ชั้น:

| ชั้นปัญหา | อาการ | ฟีเจอร์ที่ตอบ |
|---|---|---|
| **มองไม่เห็น** | ไม่รู้ว่าใครถือข้อมูลอะไรอยู่ และมันถูกส่งต่อไปไหน | แดชบอร์ด + คลังข้อมูล + Data Trail |
| **ไม่เข้าใจ** | อ่านประกาศความเป็นส่วนตัวไม่รู้เรื่อง กด "ยอมรับทั้งหมด" ทิ้ง | สาธิตการยินยอม + เกร็ดน่ารู้ |
| **ใช้สิทธิ์ไม่เป็น** | ไม่รู้ว่าขอลบยังไง ขอไปแล้วเงียบหาย ไม่รู้ว่าถึงไหน | 1-Tap Erasure + ระบบติดตามแบบพัสดุ |

### แนวคิดหลัก 3 ข้อ

**1. ยืมภาษา UX จากการติดตามพัสดุ (Package-Tracking Metaphor)**
คนไทยคุ้นกับหน้าติดตามพัสดุ Shopee/Grab อยู่แล้ว — เห็น progress bar เห็นสถานะ รู้ว่าของอยู่ไหน แอปนี้ยกรูปแบบนั้นมาใช้กับ "คำขอลบข้อมูล" แทน "พัสดุ" เพื่อสร้าง:
- **Self-efficacy** — ผู้ใช้รู้สึกว่าควบคุมได้ ไม่ใช่ยื่นเรื่องแล้วลอยหาย
- **Feedback loop** — เห็นสถานะก่อน/หลังชัดเจน ("8 องค์กรถือข้อมูล" → "7 องค์กร")
- **No dead ends** — ทุกคำขอมีสถานะที่มองเห็นได้ตลอดเวลา ไม่มีจุดที่ผู้ใช้สงสัยว่า "แล้วไงต่อ"

**2. มาสคอตเป็นผู้บรรยาย ไม่ใช่โลโก้**
จ่าใหญ่ปรากฏใน speech bubble ทุกจุดสำคัญ — สรุปสถานการณ์บนแดชบอร์ด, วิเคราะห์ความเสี่ยงรายข้อ, เตือนเมื่อเจอของอันตราย, ยินดีเมื่อภารกิจสำเร็จ บุคลิก: **จ่าใจดีแต่ตรงไปตรงมา** อบอุ่นในเรื่องทั่วไป เด็ดขาดทันทีเมื่อเจอความเสี่ยงจริง

**3. ข้อความต้นฉบับต้องไม่ถูกบิด (Content Integrity)**
ในหน้าสาธิตการยินยอม ข้อความจากประกาศความเป็นส่วนตัวแสดง **verbatim ทุกตัวอักษร ไม่ตัดทอน ไม่สรุปย่อ** — จ่าใหญ่แปลเป็นภาษาคนได้เฉพาะใน speech bubble ของตัวเองเท่านั้น และคำแปลต้องเพิ่มความชัดเจน ห้ามลดทอนความเสี่ยง

### รูปแบบการ Render

- **Static export** (`output: 'export'`) — build ออกมาเป็น HTML/JS/CSS ล้วน โฮสต์บน static host ใดก็ได้ (S3, GitHub Pages, Vercel, Netlify)
- **22 หน้าถูก pre-render** ตอน build: 6 route หลัก + 13 หน้ารายละเอียดจาก `generateStaticParams()` + not-found + icon
- **`trailingSlash: true`** เพื่อให้ deep link (`/item/xxx/`) ทำงานบน static host ที่ไม่มี rewrite rules
- **Hydration-safe** — `useNow()` คืนค่า `null` บน server และ paint แรก แล้วค่อยเริ่มเดินนาฬิกาใน `useEffect` จึงไม่มี hydration mismatch จาก `Date.now()` หรือ `localStorage`

## 3. มาสคอตจ่าใหญ่ — ระบบท่าทาง

### เกี่ยวกับตัวละคร

**จ่าใหญ่** — สารวัตรข้อมูลหนวดเทา เครื่องแบบสีน้ำตาล ติดตราที่อก สไตล์ pixel-art
**บุคลิก:** จ่าที่ดูแลลูกน้อง (= ผู้ใช้) จริง ๆ — อบอุ่นเป็นกันเองในเรื่องทั่วไป แต่เด็ดขาดตรงไปตรงมาทันทีที่เจอความเสี่ยงจริง ไม่พูดอ้อมค้อม ไม่ใช้ศัพท์กฎหมายโดยไม่จำเป็น

### การใช้งานเชิงเทคนิค

```tsx
<JaYai pose="clipboard" priority />        // โหลดก่อน (above the fold)
<JaYai pose="point" alt="" />              // ตกแต่ง — ซ่อนจาก screen reader
<JaYai pose="salute" />                    // ใช้ alt เริ่มต้นภาษาไทย
```

- Render ผ่าน `next/image` — ระบุ `width`/`height` จริงของแต่ละไฟล์เพื่อกัน layout shift (CLS)
- `image-rendering: pixelated` — ขยายแล้วคมแบบ pixel-art ไม่เบลอ
- ทุกท่ามี **alt text ภาษาไทย** เริ่มต้น (เช่น "จ่าใหญ่ส่องแว่นขยายตรวจข้อมูล") override ได้ต่อจุดใช้งาน
- Pose names เป็น TypeScript union type — พิมพ์ผิดจะ error ตอน build

### ตารางท่าทาง → บริบทการใช้งาน

| ท่า | ไฟล์ | ใช้เมื่อ | จุดที่ปรากฏจริง |
|---|---|---|---|
| `crossed` | pose_01 | กอดอก — โลโก้/แบรนด์, คำเตือนจริงจัง, น้ำเสียงจ่าเข้ม | Nav brand · การ์ดข้อมูลชีวภาพ (เสี่ยง 5/5) · เกร็ดชีวภาพ · toast ตอนปฏิเสธข้อบังคับ |
| `thumbsSmall` | pose_02 | ยกนิ้วเบา ๆ — ผลลัพธ์ที่ยอมรับได้ | การ์ดผู้ให้บริการภายนอก · toast หลังขูดการ์ดความเสี่ยงต่ำ |
| `wave` | pose_03 | โบกมือทักทาย | เจ้าบ้านหน้าเกร็ดน่ารู้ · การ์ดคุกกี้ |
| `point` | pose_04 | ชี้แนะนำ — nudge เชิงรุก | การ์ดแนะนำบนแดชบอร์ด · กล่อง "จ่าใหญ่ขอแทรก" ในหน้ารายละเอียด · การ์ดการตลาด/พันธมิตร · เกร็ดโอนต่างประเทศ |

| `magnify` | pose_07 | ส่องแว่นขยาย — กำลังตรวจ/สแกน | หัวหน้าคลังข้อมูล · การ์ดแนะนำ (สลับกับ point) · การ์ดข้อมูลเทคนิค/ตำแหน่ง · การ์ดโอนต่างประเทศ · เกร็ดตำแหน่ง |
| `think` | pose_08 | ครุ่นคิด — สถานะรอ/ว่างเปล่า | Empty state ทุกหน้า · การ์ดข้อมูลการเงิน · การ์ดระยะเวลาเก็บ · เกร็ด 10 ปี |

### เอกลักษณ์ทางภาพ — "Pixel Corner"

การ์ดและปุ่มใช้ `clip-path` ตัดมุมเป็นขั้นบันได (`--pix`, `--pix-sm`) — เชื่อมโยงกับ pixel-art ของจ่าใหญ่โดยไม่ทำให้ UI ทั้งหมดกลายเป็นเกมเรโทร ความ "พิกเซล" ถูกจำกัดไว้ที่: ตัวมาสคอต, มุมตัดของ bubble/ปุ่ม, และมิเตอร์แบบบล็อก

### โมชัน

| ค่า | รายละเอียด |

| Scroll reveal | 500–700ms + stagger 80ms/รายการ |
| Card fly-out | 340ms · Shake 450ms · Scratch fade 350ms |
| Reduced motion | `prefers-reduced-motion: reduce` ปิดทุก animation, `Reveal` แสดงทันที, `CountUp` ข้ามไปเลขจริง, การ์ดเปลี่ยนทันทีไม่ปลิว |

## 5. ฟีเจอร์ 1 — แดชบอร์ด (`/`)

หน้าแรก ตอบคำถาม "สถานการณ์ข้อมูลของฉันตอนนี้เป็นยังไง" ภายใน 5 วินาที

### 5.1 Hero Briefing — คำวินิจฉัยจากจ่าใหญ่

- จ่าใหญ่ท่าถือแฟ้ม (`clipboard`) พร้อมอนิเมชัน `bob` ลอยขึ้นลงเบา ๆ
- **หัวข้อไดนามิก:** "ข้อมูลของคุณอยู่ในมือ **8 องค์กร** รวม 12 รายการ" — ตัวเลขคำนวณสดจากรายการที่ยังไม่ถูกลบ
- **Exposure Meter** — มิเตอร์บล็อกพิกเซล 10 ช่อง + คะแนน 0–100 (ค่าเฉลี่ยความเสี่ยงของรายการที่ยังเหลือ) เปลี่ยนสีตามระดับ
- **Verdict Bubble** — ข้อความจ่าใหญ่ปรับตามสถานการณ์ 3 แบบ:

| เงื่อนไข | ข้อความ |
|---|---|
| เสี่ยงสูง ≥ 3 รายการ | "ผมไล่ดูแฟ้มแล้ว มีข้อมูลระดับ**เสี่ยงสูงถึง N รายการ**… อย่าปล่อยไว้" |
| เสี่ยงสูง 1–2 รายการ | "สถานการณ์ดีขึ้นแล้ว แต่ยังเหลือรายการเสี่ยงสูงอีก **N รายการ**" |
| ไม่เหลือเสี่ยงสูง | "**เยี่ยมมาก!** ตอนนี้ไม่เหลือรายการเสี่ยงสูงในแฟ้มของคุณแล้ว" |

### 5.2 Stat Tiles — สถิติ 4 ช่อง

| ช่อง | ค่า | สี | ไอคอน |
|---|---|---|---|
| องค์กรที่ถือข้อมูลของคุณ | นับ holder ที่ไม่ซ้ำ (เฉพาะรายการที่ยังไม่ลบ) | ขาว | อาคาร |
| รายการความเสี่ยงสูง | นับ tier = high | แดง | เตือน |
| คำขอที่กำลังดำเนินการ | สถานะ ≠ completed | ทอง | เฟือง |
| ลบสำเร็จแล้ว | สถานะ = completed | เขียว | ติ๊ก |

- ตัวเลขทุกช่อง **นับขึ้น (count-up)** ตอนโหลดครั้งแรก ด้วย cubic ease-out 800ms
- Hover: ยกขึ้น 3px + เรืองแสงไซแอน

### 5.3 คำขอที่กำลังเดินทาง — Order Tracker

แสดงคำขอล่าสุด 3 รายการเป็นการ์ดแบบติดตามพัสดุ (รายละเอียดใน [ฟีเจอร์ 4](#8-ฟีเจอร์-4--ติดตามคำขอลบข้อมูล-requests)) พร้อมลิงก์ "ดูคำขอทั้งหมด →"
ถ้ายังไม่มีคำขอ → empty state จ่าใหญ่ท่าครุ่นคิด

### 5.4 คำแนะนำเชิงรุกจากจ่าใหญ่

การ์ดสูงสุด 4 ใบ สำหรับรายการที่ **จ่าใหญ่ประเมินว่าควรลบ** และ **ยังไม่เคยส่งคำขอ**

เกณฑ์การแนะนำ (ตั้งไว้ใน `lib/data.ts` — ปัจจุบัน 5 รายการ):
- ข้อมูลเกินความจำเป็นต่อบริการ (เช่น แอปกู้เงินดูดรายชื่อผู้ติดต่อทั้งเครื่อง)
- ความสัมพันธ์สิ้นสุดแล้วแต่ข้อมูลยังอยู่ (ยิมหมดสมาชิก, ซิมเลิกใช้ 3 ปี)
- ข้อมูลอ่อนไหวที่ไม่มีฐานให้เก็บต่อ (ผลตรวจสุขภาพ)
- นายหน้าข้อมูลที่ผู้ใช้ไม่เคยให้ความยินยอมโดยตรง

แต่ละใบ: จ่าใหญ่ท่าชี้/ส่องแว่น สลับกัน · ชื่อข้อมูล + chip ความเสี่ยง · ผู้ถือ · **เหตุผลในเครื่องหมายคำพูด** (เสียงจ่าใหญ่) · ปุ่ม "ส่งคำขอลบทันที" + "ดูรายละเอียด"

กด "ส่งคำขอลบทันที" → สร้างคำขอ, toast จ่าใหญ่วันทยหัตถ์, **เลื่อนหน้าจอลงไปที่ตัวติดตามอัตโนมัติ** (ปิด feedback loop ให้เห็นผลทันที)
เมื่อจัดการครบทุกใบ → empty state "ภารกิจครบถ้วน!" จ่าใหญ่วันทยหัตถ์

## 6. ฟีเจอร์ 2 — คลังข้อมูลของฉัน (`/inventory`)

รายการข้อมูลส่วนบุคคลทั้งหมด **13 รายการ** จาก **8 องค์กร** เรียงตามคะแนนความเสี่ยงจากมากไปน้อย

### 6.1 ตัวกรอง 5 แบบ

`ทั้งหมด` · `จ่าใหญ่แนะนำให้ลบ` · `เสี่ยงสูง` · `เสี่ยงปานกลาง` · `เสี่ยงต่ำ`
ใช้ `aria-pressed` เพื่อบอกสถานะกับ screen reader · ปุ่มที่เลือกอยู่พื้นทอง

### 6.2 โครงสร้างแต่ละแถว

```
[ไอคอน]  ชื่อข้อมูล                      ส่งต่อ 3 ทอด → ดาต้าลิงก์  [chip]  [→]
         ผู้ถือ · ประเภทองค์กร
         ⚠ จ่าใหญ่แนะนำให้ส่งคำขอลบ
```

| องค์ประกอบ | รายละเอียด |
|---|---|
| **ไอคอน** | ตามชนิดข้อมูล (โทรศัพท์, บัตรประชาชน, ตำแหน่ง, สุขภาพ, ซิม, ตะกร้า…) ใน badge สีอินดิโก้ |
| **ชื่อข้อมูล + ผู้ถือ** | สองบรรทัดแยกชัดเจน (`display: block`) |
| **ธงแนะนำ** | แสดงเฉพาะรายการที่แนะนำและยังไม่ส่งคำขอ |
| **Data Trail ย่อ** | นับจำนวนทอดที่ถูกส่งต่อ + ปลายทางสุดท้าย (สีส้ม) — หรือ "เก็บไว้ที่ผู้ให้บริการเท่านั้น" |
| **Chip ขวาสุด** | ถ้ามีคำขอ → chip สถานะ DSR · ถ้ายังไม่มี → chip ระดับความเสี่ยง |
| **สถานะลบแล้ว** | แถวจางลง (opacity 0.55) ไอคอนเปลี่ยนเป็นเขียว |

- **อัปเดตสด** — poll ทุก 1.5 วินาที เพื่อให้ chip สถานะขยับตามคำขอที่กำลังวิ่ง
- Hover: ยกขึ้น + เรืองแสงไซแอน + ลูกศรเลื่อนขวา
- บนมือถือ: ซ่อนคอลัมน์ Data Trail เหลือ 3 คอลัมน์

## 7. ฟีเจอร์ 3 — หน้ารายละเอียดข้อมูล (`/item/[id]`)

หน้านี้ถูก **pre-render ครบทั้ง 13 รายการ** ตอน build ผ่าน `generateStaticParams()` — เปิด deep link ตรง ๆ ได้ทันที มี metadata (title) แยกต่อหน้า

แบ่ง 2 คอลัมน์บนเดสก์ท็อป (ซ้อนกันบนมือถือ)

### 7.1 คอลัมน์ซ้าย — ข้อเท็จจริง

**การ์ดหัวเรื่อง:** ไอคอน + ชื่อข้อมูล + ผู้ถือ + Exposure Meter (0–100) + chip ความเสี่ยง + สถานะล่าสุด (เช่น "แอปยังเปิดสิทธิ์เข้าถึงอยู่", "เลิกใช้เบอร์นี้มา 3 ปี")

**การ์ด Data Trail — เส้นทางของข้อมูล**
ไทม์ไลน์แนวตั้งแสดงว่าข้อมูลชิ้นนี้เดินทางไปไหนมาบ้าง แต่ละสเต็ปมี 4 ชั้นข้อมูล: ประเภท → องค์กร → คำอธิบาย → ช่วงเวลา

| ประเภท | ป้าย | สีเส้นขอบ | ความหมาย |
|---|---|---|---|
| `collect` | จัดเก็บ / COLLECTED | ไซแอน | เก็บจากผู้ใช้โดยตรง |
| `store` | เก็บรักษา / STORED | ไซแอน | เก็บอยู่ในระบบ |
| `share` | ส่งต่อ / SHARED | ส้ม | ส่งให้บุคคลที่สาม |
| `broker` | นายหน้าข้อมูล / BROKER | **แดง** | ปลายทางที่ข้อมูลถูกขายต่อ |

> ตัวอย่างเส้นทางจริงในระบบ: เบอร์โทรศัพท์ → ช้อปมาลี (เก็บตอนสมัคร) → ระบบสมาชิก (ใช้ OTP) → **ดาต้าลิงก์ อินไซต์** (ถูกส่งต่อเพื่อการตลาด)

### 7.2 คอลัมน์ขวา — บทวิเคราะห์และการลงมือ

**บทวิเคราะห์ AI (เสียงจ่าใหญ่)**
จ่าใหญ่ท่าชูหลอดไฟ + speech bubble หัวข้อ "จ่าใหญ่วิเคราะห์ · Exposure Score NN/100"
เนื้อหาเป็นภาษาพูด อธิบายว่า *ถ้าปล่อยไว้จะเกิดอะไรขึ้น* ไม่ใช่ศัพท์กฎหมาย เช่น:

> "แอปกู้เงินดูดรายชื่อเพื่อนคุณไปทั้งเครื่องตั้งแต่วันสมัคร ถ้าข้อมูลชุดนี้หลุด เพื่อนกับครอบครัวคุณจะโดนแก๊งทวงหนี้และมิจฉาชีพโทรหาแทนคุณ ผมไม่ปล่อยผ่านแน่"

**Nudge เชิงรุก** (เฉพาะรายการที่แนะนำ)
กล่อง "จ่าใหญ่ขอแทรก" — จ่าใหญ่ท่าชี้ + เหตุผลตัวหนา + "อย่ารอช้า ผมแนะนำให้กดส่งเลย"

**ปุ่ม 1-Tap Erasure**
ปุ่มทองเต็มความกว้าง สูง 56px: `🗑 1-Tap ส่งคำขอลบข้อมูล`
ใต้ปุ่มมีคำอธิบายสิทธิ์: "ส่งคำขอใช้สิทธิ์ลบ (Right to Erasure) ผ่าน Standardized DSR API ไปยัง [องค์กร] · องค์กรต้องตอบภายใน 30 วันตาม PDPA"

**หลังกดส่ง** — ปุ่มถูกแทนที่ด้วยตัวติดตามสถานะสด (stepper + SLA bar) และข้อความจ่าใหญ่ตามสถานะ:

| สถานะ | ข้อความ |
|---|---|
| ส่งคำขอแล้ว | "คำขอถูกส่งถึง [องค์กร] แล้ว — รอองค์กรยืนยันรับเรื่อง" |
| กำลังดำเนินการ | "[องค์กร] กำลังดำเนินการลบ — จ่าใหญ่เฝ้าติดตามให้อยู่ **ไม่มีหายเงียบแน่นอน**" |
| ลบสำเร็จ | Banner เขียว จ่าใหญ่วันทยหัตถ์: "ภารกิจสำเร็จ — [องค์กร] ลบข้อมูลของคุณแล้ว" |

### 7.3 กรณี ID ไม่ถูกต้อง

Empty state จ่าใหญ่ท่าครุ่นคิด "ไม่พบรายการนี้ในแฟ้ม" + ปุ่มกลับไปคลังข้อมูล — ไม่มีหน้าจอค้างหรือ error ดิบ

## 8. ฟีเจอร์ 4 — ติดตามคำขอลบข้อมูล (`/requests`)

หน้าประวัติคำขอทั้งหมด เลียนแบบหน้า "คำสั่งซื้อของฉัน" ของ Shopee

### 8.1 แท็บกรอง

`ทั้งหมด` · `กำลังดำเนินการ` · `สำเร็จแล้ว` — เรียงคำขอใหม่สุดขึ้นก่อน

### 8.2 กายวิภาคของการ์ดติดตาม

```
ชื่อข้อมูล (ลิงก์)  · องค์กร · ยื่นเมื่อ 26 ก.ค. 69          [chip สถานะ]
────────────────────────────────────────────────────────────
   ✈──────────────────⚙──────────────────✓
ส่งคำขอแล้ว      กำลังดำเนินการ      ลบข้อมูลสำเร็จ
────────────────────────────────────────────────────────────
กรอบเวลาตามกฎหมาย 30 วัน · ครบกำหนด 25 ส.ค. 69      วันที่ 4/30
▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
```

**Stepper 3 ขั้น** — จุดที่ผ่านแล้วเป็นทอง, ขั้นปัจจุบันมี **pulse animation**, ขั้นสุดท้ายเมื่อสำเร็จเป็นเขียว, เส้นเชื่อมเติมจากซ้ายไปขวา (transition 800ms)
`role="list"` + `aria-label` เพื่อให้ screen reader อ่านลำดับได้

**แถบ SLA 30 วัน** — แสดงกรอบเวลาตามกฎหมาย PDPA พร้อมวันครบกำหนดจริง (คำนวณจากวันยื่น + 30 วัน) และวันที่ปัจจุบันในรูปแบบ "วันที่ 4/30" · ลายทางแบบพิกเซล เปลี่ยนจากทองเป็นเขียวเมื่อสำเร็จ

**Empty state** — จ่าใหญ่ท่าครุ่นคิด + ปุ่มไปคลังข้อมูล (ไม่มีทางตัน)

## 9. ฟีเจอร์ 5 — สาธิตการยินยอม (`/consent`)

> **แท็บ BETA** — ปุ่มทองใน nav bar (ใช้ slot CTA ตาม style guide)

### 9.1 ปัญหาที่แก้

ประกาศความเป็นส่วนตัวปกติ = กำแพงตัวหนังสือ + ปุ่ม "ยอมรับทั้งหมด" ปุ่มเดียว → ผู้ใช้กดผ่านโดยไม่อ่าน และไม่มีทางเลือกรายข้อ
**วิธีแก้:** แตกประกาศเป็นการ์ดปัดแบบ Tinder — **1 ข้อ = 1 การ์ด** ยอมรับหรือปฏิเสธเป็นราย ๆ

### 9.2 กฎเหล็กเรื่องเนื้อหา (Content Integrity)

| ส่วน | กฎ |
|---|---|
| **ข้อความประกาศ** | Verbatim 100% จาก `privacy-notice-source-th.md` — ห้ามตัด ห้ามย่อ ห้ามเรียบเรียงใหม่ |
| **Speech bubble จ่าใหญ่** | ที่เดียวที่แปลเป็นภาษาคนได้ — และต้องเพิ่มความชัดเจน **ห้ามลดทอนความเสี่ยง** |
| **การแยกทางสายตา** | ข้อความทางการแสดงบน**พื้นกระดาษสีสว่าง** ขอบทองซ้าย ต่างจาก UI มืดทั้งหมด — ผู้ใช้แยกออกทันทีว่าอันไหน "ข้อความจริง" อันไหน "จ่าใหญ่พูด" |

ข้อความทุกชิ้นเก็บใน `lib/notice.ts` เป็น structured blocks (`heading` / `text` / `bullet` / `row`) โดย `row` ใช้เรนเดอร์ตารางฐานกฎหมายจากมาตรา 3 (วัตถุประสงค์ / ข้อมูลที่ใช้ / ฐานกฎหมาย)

> **หมายเหตุเรื่องรหัส `CHUNK-xx`:** รหัสนี้เป็น **ข้อมูลภายในสำหรับตรวจสอบย้อนกลับ** ว่าการ์ดแต่ละใบตรงกับส่วนไหนของเอกสารต้นฉบับ — เก็บไว้ใน `lib/notice.ts` แต่**ไม่แสดงบนหน้าจอผู้ใช้** เพราะเป็นศัพท์เชิงเทคนิคที่ไม่มีความหมายกับคนทั่วไป ตารางด้านล่างอ้างอิงรหัสนี้เพื่อให้ทีมพัฒนาตรวจทานกับต้นฉบับได้

**สรุป:** บังคับ 6 · เลือกได้ 5 · รับทราบอย่างเดียว 1

### 9.4 การควบคุม — 3 ช่องทางเท่าเทียมกัน

| ช่องทาง | ยอมรับ | ปฏิเสธ |
|---|---|---|
| **ปัดนิ้ว/เมาส์** | ปัดขวา ≥ 110px | ปัดซ้าย ≥ 110px |
| **ปุ่ม** | `✓ ยอมรับ` | `✕ ปฏิเสธ` |
| **คีย์บอร์ด** | `→` | `←` |

**รายละเอียด gesture:**
- ใช้ Pointer Events — รองรับทั้ง touch, mouse, stylus ด้วยโค้ดชุดเดียว
- `touch-action: pan-y` — เลื่อนหน้าจอแนวตั้งยังทำงานปกติ (ตามหลัก UX ที่ว่าห้าม override system gesture)
- แยกเจตนา: ต้องลากแนวนอน ≥ 10px **และ** มากกว่าแนวตั้ง จึงจะเริ่มนับเป็นการปัด
- ระหว่างลาก: การ์ดเอียงตามระยะ (`rotate = dx × 0.06`) + **ตราประทับ** "ยอมรับ" (เขียว) / "ปฏิเสธ" (แดง) จางเข้าตามระยะทาง
- ปล่อยไม่ถึงเกณฑ์ → เด้งกลับที่เดิม
- ผ่านเกณฑ์ → การ์ดปลิวออก 340ms แล้วขึ้นใบถัดไป
- มีการ์ด ghost ซ้อนด้านหลัง 2 ใบ ให้เห็นว่ายังมีต่อ

### 9.5 การ์ดบังคับ (Mandatory Lock)

การ์ดที่ปฏิเสธไม่ได้ตามกฎหมาย/ตามหน้าที่ของบริการ:
- ปุ่มเปลี่ยนเป็นปุ่มเดียว: **"รับทราบ ไปข้อถัดไป"**
- ปัดซ้าย/กด `←` → การ์ด **สั่น 450ms** + toast จ่าใหญ่ท่ากอดอก บอกเหตุผลทันที
- แสดง**กล่องเหตุผลถาวร**บนการ์ดเสมอ (ไม่ต้องลองผิดก่อนถึงจะรู้):

> 🛡 **ทำไมข้อนี้ปฏิเสธไม่ได้?**
> "ตัวอย่างง่าย ๆ: แอปส่งของต้องบอกที่อยู่คุณให้บริษัทขนส่ง ไม่งั้นของไปไม่ถึงบ้าน — การส่งต่อให้ผู้ประมวลผลจึงจำเป็นต่อการให้บริการ"

### 9.6 การ์ดขูด (Digital Scratch Card)

ใช้กับ 2 ข้อที่ต้องการให้ผู้ใช้ "หยุดคิดจริง ๆ" — CHUNK-10 (โอนข้อมูลต่างประเทศ) และ CHUNK-11 (เก็บ 10 ปี)

| ด้าน | รายละเอียด |

| **หน้าตา** | Canvas ฟอยล์ทองพร้อมลายทางเฉียง เลียนแบบลอตเตอรี่ขูดไทย/รางวัล Shopee |

## 10. ฟีเจอร์ 6 — เกร็ดน่ารู้ (`/insights`)

### 10.1 ทฤษฎีเบื้องหลัง

อ้างอิง **Curiosity-Gap Theory (Loewenstein, 1994)** — คนจะแสวงหาข้อมูลเมื่อรับรู้ว่ามี "ช่องว่าง" ระหว่างสิ่งที่รู้กับสิ่งที่อยากรู้ ผสมกับรูปแบบการเสพเนื้อหาแบบ TikTok/Duolingo

**จุดต่างจากฟีเจอร์ 5:** หน้านี้ทำหน้าที่ **ให้ความรู้เท่านั้น** ไม่มีปุ่มยอมรับ/ปฏิเสธใด ๆ

### 10.2 การ์ดทั้ง 5 ใบ

ทุกใบดึงจุดเสี่ยงจริงจากประกาศฉบับเดียวกัน:

| # | อ้างอิงต้นฉบับ | Hook (คำที่ไฮไลต์ทอง) | ท่าจ่าใหญ่ | ชั้นเนื้อหา |
|---|---|---|---|---|
| 1 | CHUNK-04 | "รู้หรือไม่? แอปนี้เก็บ**ตำแหน่งของคุณ**แนบไปกับข้อมูลเทคนิคธรรมดา ๆ" | magnify | 3 ชั้น + อ้างอิง |
| 2 | CHUNK-10 | "ข้อมูลของคุณอาจไม่ได้อยู่ใน**ประเทศไทย**ด้วยซ้ำ" | point | 2 ชั้น + อ้างอิง |
| 3 | CHUNK-03 | "รหัสผ่านหลุดยังเปลี่ยนได้ แต่**ใบหน้าของคุณ**เปลี่ยนไม่ได้ตลอดชีวิต" | crossed | 3 ชั้น + อ้างอิง |
| 4 | CHUNK-11 | "ลบแอปวันนี้ ข้อมูลการเงินของคุณยังอยู่กับเขาอีก**10 ปี**" | think | 3 ชั้น + อ้างอิง |
| 5 | CHUNK-12 | "ประกาศนี้พูดถึง**คุกกี้**แค่ 2 บรรทัด — น้อยไปสำหรับตัวตามรอยคุณทั้งเว็บ" | wave | 2 ชั้น + อ้างอิง |

### 10.3 กลไกเปิดทีละชั้น (Progressive Reveal)

ผู้ใช้แตะเปิดทีละชั้น ไม่เทข้อมูลทั้งหมดพร้อมกัน — ลด cognitive load และเพิ่มความเข้าใจ

```
[Hook]  →  แตะ "แตะเพื่อดูคำตอบ"
        →  ชั้น 1: เกิดอะไรขึ้น       (แตะ "แล้วไงต่อ?")
        →  ชั้น 2: ทำไมต้องสนใจ       (แตะ "แล้วไงต่อ?")
        →  ชั้น 3: ทำอะไรได้          (แตะ "ขอดูข้อความจริงในประกาศ")
        →  ชั้น 4: ข้อความ verbatim จากประกาศ
        →  จ่าใหญ่สรุป + ลิงก์ไปสาธิตการยินยอม
```

- ป้ายปุ่มเปลี่ยนตามชั้นที่เปิดอยู่ — บอกใบ้ว่ายังมีอะไรรออยู่ (สร้าง curiosity gap ต่อเนื่อง)
- แต่ละชั้นเข้าด้วย animation `layer-in` 300ms (fade + slide + scale เล็กน้อย)
- **ชั้นสุดท้ายเป็นข้อความ verbatim จากประกาศเสมอ** — ปิดวงจรด้วยหลักฐานจริง ไม่ใช่แค่คำบอกเล่า
- เปิดครบ → จ่าใหญ่สรุป + ปุ่มไปหน้าสาธิตการยินยอม
- ใช้ `aria-expanded` บอกสถานะกับ screen reader · แต่ละการ์ดเป็น `<button>` เต็มขนาด กดด้วยคีย์บอร์ดได้

## 11. ระบบเบื้องหลัง — จำลอง DSR API

### 11.1 การเก็บสถานะ

- เก็บใน `localStorage` คีย์ **`jayai-state-v1`** — สถานะคงอยู่ข้ามหน้าและข้ามการรีเฟรช
- โครงสร้าง: `{ requests: { [itemId]: { submittedAt: number } } }` — เก็บแค่ timestamp แล้ว**คำนวณสถานะสดทุกครั้ง** ไม่มี state ซ้ำซ้อนให้หลุด sync

### 11.2 การไล่สถานะ (Simulated Progression)

| เวลาจริงหลังส่ง | สถานะ | เทียบเป็นวันใน SLA |
|---|---|---|
| 0–8 วินาที | ส่งคำขอแล้ว (Submitted) | วันที่ 1–2 |
| 8–40 วินาที | กำลังดำเนินการ (Processing) | วันที่ 2–8 |
| ≥ 40 วินาที | ลบข้อมูลสำเร็จ (Completed) | วันที่ 9 (คงที่) |

- **มาตราส่วนเวลา:** 5 วินาทีจริง ≈ 1 วันตาม SLA (SLA จริง = 30 วันตาม PDPA)
- วันครบกำหนดที่แสดงเป็น **วันที่จริง** (วันยื่น + 30 วัน) เพื่อให้ตัวเลขน่าเชื่อถือในการเดโม

### 11.3 ข้อมูลตั้งต้น (Seeding)

เปิดแอปครั้งแรกจะ seed คำขอไว้ 2 รายการอัตโนมัติ:
- `phone-bigmart` — ยื่นมาแล้ว 2 วัน → **สำเร็จแล้ว** (ให้เห็น win state ทันที)
- `citizenid-connectel` — ยื่นมาแล้ว 15 วินาที → **กำลังดำเนินการ** (ให้เห็นสถานะขยับสด ๆ ระหว่างเดโม)

> ล้างสถานะเดโม: `localStorage.removeItem('jayai-state-v1')` ใน DevTools แล้วรีเฟรช

### 11.4 นาฬิกากลาง — `useNow()` hook

```ts
const now = useNow();        // null บน server → number หลัง mount
const now = useNow(1500);    // ปรับ interval ได้ (คลังข้อมูลใช้ 1.5 วิ)
```

แทนที่รูปแบบเดิม (`setInterval` แล้ว re-render ทั้งหน้า) ด้วย hook เดียวที่ให้ timestamp — component คำนวณสถานะจากค่านั้นเอง ทำให้:
- ไม่มี hydration mismatch (server ได้ `null` เสมอ)
- ไม่มีการรีเซ็ต hover/animation จากการ re-render ทั้ง DOM
- ทดสอบง่าย — ทุกฟังก์ชันใน `store.ts` รับ `now` เป็นพารามิเตอร์ได้

### 11.5 ระบบ Toast

`Toaster.tsx` ใช้ CustomEvent bus — component ไหนก็เรียก `toast(ข้อความ, ท่าจ่าใหญ่)` ได้โดยไม่ต้องส่ง props ลงไปเป็นทอด ๆ
Toast แสดง 3.6 วินาที · มี `role="status"` เพื่อให้ screen reader ประกาศ · มีจ่าใหญ่ท่าที่เหมาะกับสถานการณ์ทุกครั้ง

| **≤ 640px** | Nav wrap หลายบรรทัด · Hero มาสคอตย้ายไปใต้ข้อความ · สถิติ 2 คอลัมน์ · ซ่อนคอลัมน์ Data Trail ในคลังข้อมูล · การ์ดยินยอม padding ลด · สรุปผลเหลือ 2 คอลัมน์ · มาสคอตย่อขนาด |

## 14. ความสอดคล้องกับ PDPA

| สิทธิ์ตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | การรองรับในแอป |
|---|---|
| **สิทธิ์ในการเข้าถึง** (Right to Access) | คลังข้อมูล + หน้ารายละเอียด แสดงว่าใครถืออะไร |
| **สิทธิ์ในการลบ** (Right to Erasure) | ปุ่ม 1-Tap Erasure + ระบบติดตาม 30 วัน ✅ **ฟีเจอร์หลัก** |
| **สิทธิ์ในการถอนความยินยอม** (Right to Withdraw Consent) | หน้าสาธิตการยินยอม — ปฏิเสธรายข้อได้ |
| **สิทธิ์ในการคัดค้าน** (Right to Object) | การ์ด "เกินมาตรฐาน" (CHUNK-06) เปิดให้ opt-out จากฐานประโยชน์โดยชอบ |
| **การแจ้งข้อมูล** (Transparency) | Data Trail แสดงการส่งต่อข้ามองค์กร + เกร็ดน่ารู้อธิบายจุดเสี่ยง |
| **กรอบเวลา 30 วัน** | แถบ SLA แสดงวันครบกำหนดจริงทุกคำขอ |

**หลักการที่แอปสาธิต:**
- **Granular consent** — ยินยอมรายข้อ ไม่ใช่ยอมรับทั้งหมดปุ่มเดียว
- **Informed consent** — ต้องเห็นข้อความจริงและเข้าใจก่อนตัดสินใจ
- **แยกฐานกฎหมายให้ชัด** — ข้อที่ใช้ฐานสัญญา/กฎหมายจะไม่หลอกถามความยินยอม แต่บอกตรง ๆ ว่าปฏิเสธไม่ได้พร้อมเหตุผล (ตรงข้ามกับ dark pattern ที่ทำให้ทุกอย่างดูเหมือนเลือกได้)
