# จ่าใหญ่ (Ja Yai) — Product Feature Inventory

> **เอกสารนี้คืออะไร:** รายการความสามารถ (capability) ทั้งหมดของผลิตภัณฑ์ เขียนสำหรับใช้เป็นวัตถุดิบในการวิเคราะห์ธุรกิจ — **ไม่มีรายละเอียดด้านโค้ด สี ฟอนต์ หรือ accessibility**
> **เอกสารนี้ไม่ทำอะไร:** ไม่วิเคราะห์โมเดลธุรกิจ ไม่เสนอราคา ไม่ระบุกลุ่มลูกค้าเป้าหมาย — เป็นการบรรยายสิ่งที่ระบบทำได้ตามข้อเท็จจริงเท่านั้น
> **สถานะ:** ต้นแบบใช้งานได้จริง (working prototype) สำหรับ PDPA Hackathon 2026

---

## 0. สรุปผลิตภัณฑ์ใน 60 วินาที

**จ่าใหญ่** คือเครื่องมือที่ทำให้ "สิทธิ์ตาม PDPA" กลายเป็นสิ่งที่คนธรรมดากดใช้ได้จริง แทนที่จะเป็นข้อความในเอกสารกฎหมาย

ระบบทำ 3 อย่าง:

| # | ความสามารถหลัก | คำอธิบายสั้น |
|---|---|---|
| **A** | **มองเห็น** (Visibility) | แสดงว่าใครถือข้อมูลส่วนบุคคลของคุณอยู่บ้าง แต่ละชิ้นเสี่ยงแค่ไหน และถูกส่งต่อไปที่ไหนแล้ว |
| **B** | **ลงมือ** (Action) | กดปุ่มเดียวส่งคำขอใช้สิทธิ์ลบข้อมูล แล้วติดตามสถานะแบบเดียวกับติดตามพัสดุ จนกว่าจะเสร็จ |
| **C** | **เข้าใจ** (Comprehension) | แปลงประกาศความเป็นส่วนตัวจากกำแพงตัวหนังสือ เป็นการ์ดที่อ่านทีละข้อและเลือกยินยอมเป็นราย ๆ |

**องค์ประกอบร่วม:** มาสคอต "จ่าใหญ่" ทำหน้าที่เป็นผู้บรรยายตลอดทั้งระบบ — อธิบายความเสี่ยงเป็นภาษาพูด ไม่ใช่ศัพท์กฎหมาย

---

## 1. ข้อเท็จจริงเรื่องรูปแบบการติดตั้ง (สำคัญต่อการวิเคราะห์)

> ส่วนนี้ระบุข้อเท็จจริงที่มีผลต่อการคิดโมเดลธุรกิจ — ไม่ได้เสนอแนวทาง

| หัวข้อ | สถานะปัจจุบัน |
|---|---|
| **รูปร่างของแอปตอนนี้** | เว็บแอปเดี่ยว (standalone) หน้าตาแบบ **consumer-facing** — ผู้ใช้ปลายทางเปิดเองแล้วเห็นข้อมูลตัวเอง |
| **สถาปัตยกรรม** | Static export — build ออกมาเป็นไฟล์ HTML/JS/CSS ล้วน ไม่มี server ของตัวเอง โฮสต์ที่ไหนก็ได้ |
| **Backend** | **ไม่มี** — สถานะทั้งหมดเก็บใน browser (localStorage) ของเครื่องผู้ใช้ |
| **ระบบยืนยันตัวตน** | **ไม่มี** |
| **การเชื่อมต่อภายนอก** | **ไม่มี** — ยังไม่ต่อกับ API หรือฐานข้อมูลจริงใด ๆ |
| **ความสามารถในการฝังในแอปอื่น** | ยังไม่ได้ทำเป็น SDK/widget/iframe — ปัจจุบันเป็นเว็บทั้งเว็บ แต่แต่ละฟีเจอร์แยกเป็นหน้าอิสระ (`/consent`, `/insights` ฯลฯ) และแยกเป็นคอมโพเนนต์อยู่แล้ว |
| **ภาษา** | ไทยเป็นหลัก (ใช้อังกฤษเฉพาะศัพท์เทคนิค) |

**ข้อสังเกตที่เป็นข้อเท็จจริง:** ฟีเจอร์ 6 อย่างในระบบ **ไม่ได้อยู่ในหมวดเดียวกันทั้งหมด** — บางอย่างเป็นเครื่องมือฝั่งผู้บริโภค (ดูข้อมูลตัวเอง, ส่งคำขอลบ) บางอย่างเป็นส่วนติดต่อที่องค์กรต้องมีอยู่แล้วตามกฎหมาย (หน้าขอความยินยอม) ความต่างนี้มีผลต่อว่าใครคือคนจ่ายเงิน

---

## 2. รายการฟีเจอร์ทั้งหมด

### ฟีเจอร์ 1 — แดชบอร์ดภาพรวมความเสี่ยง

**ทำอะไร:** หน้าแรกที่ตอบคำถาม "ตอนนี้ข้อมูลของฉันอยู่ในมือใครบ้าง และน่าห่วงแค่ไหน"

**ผู้ใช้เห็นอะไร:**
- จำนวนองค์กรที่ถือข้อมูลอยู่ + จำนวนรายการข้อมูลทั้งหมด
- **คะแนนความเสี่ยงรวม 0–100** พร้อมมิเตอร์ภาพ
- คำวินิจฉัยจากจ่าใหญ่ — ข้อความเปลี่ยนตามสถานการณ์จริง (เสี่ยงสูงหลายรายการ / เหลือน้อย / ปลอดภัยแล้ว)
- ตัวเลขสรุป 4 ช่อง: องค์กรที่ถือข้อมูล · รายการเสี่ยงสูง · คำขอที่กำลังดำเนินการ · ลบสำเร็จแล้ว
- คำขอลบข้อมูลที่กำลังดำเนินการ (แสดงแบบติดตามพัสดุ)
- **รายการที่ระบบแนะนำให้ลบ** พร้อมเหตุผล และปุ่มส่งคำขอทันทีจากหน้านี้เลย

**ต้องมีอะไรถึงจะทำงานได้จริง:** แหล่งข้อมูลว่าองค์กรใดถือข้อมูลอะไรของผู้ใช้คนนี้ (ปัจจุบันเป็นข้อมูลจำลอง)

**คุณค่าที่ส่งมอบ:** ทำให้ความเสี่ยงที่มองไม่เห็น กลายเป็นตัวเลขเดียวที่เข้าใจได้ทันที และเห็นความคืบหน้าเมื่อจัดการไปเรื่อย ๆ

---

### ฟีเจอร์ 2 — คลังข้อมูลส่วนบุคคล (Data Inventory)

**ทำอะไร:** รายการข้อมูลส่วนบุคคลทุกชิ้นที่บุคคลที่สามถืออยู่ เรียงตามความเสี่ยง

**ผู้ใช้เห็นอะไร (ต่อ 1 รายการ):**
- **ข้อมูลอะไร** — เช่น เบอร์โทร, เลขบัตรประชาชน, ประวัติตำแหน่ง, ข้อมูลสุขภาพ, รายชื่อผู้ติดต่อ
- **ใครถือ** — ชื่อองค์กร + ประเภทธุรกิจ
- **ถูกส่งต่อไปกี่ทอดแล้ว และปลายทางล่าสุดคือใคร**
- ระดับความเสี่ยง หรือสถานะคำขอลบ (ถ้ายื่นไปแล้ว)
- ธงเตือนถ้าระบบประเมินว่าควรลบ

**ตัวกรอง:** ทั้งหมด · ระบบแนะนำให้ลบ · เสี่ยงสูง · ปานกลาง · ต่ำ

**ต้องมีอะไรถึงจะทำงานได้จริง:** แหล่งข้อมูลเดียวกับฟีเจอร์ 1 + ข้อมูลว่าองค์กรส่งต่อข้อมูลให้ใครบ้าง (ROPA / Data Mapping ขององค์กร)

**คุณค่าที่ส่งมอบ:** เปลี่ยน "ไม่รู้ว่าใครมีข้อมูลเราบ้าง" เป็นรายการที่ตรวจสอบได้ทีละชิ้น

---

### ฟีเจอร์ 3 — เส้นทางข้อมูล + บทวิเคราะห์ + ปุ่มลบ (หน้ารายละเอียด)

**ทำอะไร:** เจาะลึกข้อมูล 1 ชิ้น — ว่ามันเดินทางไปไหนมาแล้ว เสี่ยงยังไง และลงมือจัดการได้เลย

**3 ส่วนประกอบ:**

**3.1 Data Trail — เส้นทางการไหลของข้อมูล**
ไทม์ไลน์แสดงว่าข้อมูลชิ้นนี้ถูก **จัดเก็บ → เก็บรักษา → ส่งต่อ → ไปถึงนายหน้าข้อมูล** โดยระบุชื่อองค์กรและช่วงเวลาในแต่ละทอด
> ตัวอย่างจริงในระบบ: เบอร์โทรศัพท์ → ร้านค้าออนไลน์ (เก็บตอนสมัคร) → ระบบสมาชิก (ใช้ยืนยัน OTP) → **นายหน้าข้อมูล** (ถูกส่งต่อเพื่อการตลาด)

**3.2 บทวิเคราะห์ความเสี่ยงเป็นภาษาพูด**
คะแนนความเสี่ยงเฉพาะชิ้น (0–100) + คำอธิบายว่า *ถ้าปล่อยไว้จะเกิดอะไรขึ้น* โดยเล่าเป็นสถานการณ์จริง ไม่ใช่ศัพท์กฎหมาย
> ตัวอย่าง: "แอปกู้เงินดูดรายชื่อเพื่อนคุณไปทั้งเครื่องตั้งแต่วันสมัคร ถ้าข้อมูลชุดนี้หลุด เพื่อนกับครอบครัวคุณจะโดนแก๊งทวงหนี้และมิจฉาชีพโทรหาแทนคุณ"

**3.3 ปุ่มส่งคำขอลบข้อมูล 1 ครั้ง (1-Tap Erasure)**
กดครั้งเดียว = ยื่นคำขอใช้สิทธิ์ลบข้อมูล (Right to Erasure) ไปยังองค์กรนั้น

**ต้องมีอะไรถึงจะทำงานได้จริง:**
- Data Trail ต้องได้ข้อมูลการส่งต่อจากองค์กร (ROPA)
- บทวิเคราะห์ปัจจุบันเป็นข้อความที่เขียนไว้ล่วงหน้า — ถ้าทำจริงเป็น LLM generate ได้
- ปุ่มลบต้องต่อกับช่องทางรับคำขอจริงขององค์กร (API / อีเมล DPO / ระบบ DSR)

**คุณค่าที่ส่งมอบ:** ย่นระยะจาก "รู้ว่ามีสิทธิ์" ไปสู่ "ใช้สิทธิ์แล้ว" เหลือการกดปุ่มเดียว

---

### ฟีเจอร์ 4 — ระบบติดตามคำขอแบบพัสดุ (DSR Tracking)

**ทำอะไร:** ติดตามคำขอใช้สิทธิ์ทุกใบ ตั้งแต่ยื่นจนจบ ด้วยรูปแบบที่คนไทยคุ้นอยู่แล้วจากการติดตามพัสดุ

**ผู้ใช้เห็นอะไร:**
- **แถบสถานะ 3 ขั้น:** ส่งคำขอแล้ว → กำลังดำเนินการ → ลบข้อมูลสำเร็จ
- **แถบนับถอยหลัง SLA 30 วัน** ตามที่กฎหมาย PDPA กำหนด พร้อมวันครบกำหนดจริง
- ประวัติคำขอทั้งหมด แยกแท็บ: ทั้งหมด / กำลังดำเนินการ / สำเร็จแล้ว
- **หลักการ "ไม่มีทางตัน"** — ทุกคำขอต้องมีสถานะที่มองเห็นได้เสมอ ไม่มีจุดที่ผู้ใช้ไม่รู้ว่าเรื่องไปถึงไหน

**ต้องมีอะไรถึงจะทำงานได้จริง:** ช่องทางรับสถานะกลับจากองค์กรผู้ถือข้อมูล (webhook / polling / อัปเดตด้วยมือจากฝั่ง DPO)

**คุณค่าที่ส่งมอบ:**
- ฝั่งผู้ใช้: ความมั่นใจว่าเรื่องไม่หายเงียบ
- ฝั่งองค์กร: หลักฐานว่าตอบคำขอภายในกรอบเวลาที่กฎหมายกำหนด (audit trail)

---

### ฟีเจอร์ 5 — สาธิตการยินยอมแบบการ์ดปัด (Privacy Notice Demo)

**ทำอะไร:** แทนที่ประกาศความเป็นส่วนตัวแบบ "กำแพงตัวหนังสือ + ปุ่มยอมรับทั้งหมด" ด้วยการ์ดที่อ่านทีละข้อและเลือกยินยอมเป็นราย ๆ

**กลไก:**
- **1 ข้อในประกาศ = 1 การ์ด** (ระบบปัจจุบันมี 12 การ์ดจากประกาศตัวอย่าง 1 ฉบับ)
- ปัดขวา = ยอมรับ · ปัดซ้าย = ปฏิเสธ (มีปุ่มกดและคีย์บอร์ดเป็นทางเลือกเท่าเทียมกัน)
- แต่ละการ์ดแสดง **ข้อความจากประกาศฉบับจริงแบบไม่ตัดทอนแม้แต่คำเดียว** บนพื้นที่หน้าตาเหมือนกระดาษราชการ + คำแปลภาษาพูดจากจ่าใหญ่แยกออกมาชัดเจน + คะแนนความเสี่ยง 1–5 พร้อมเหตุผล

**การแยกฐานทางกฎหมาย (จุดที่ต่างจาก consent tool ทั่วไป):**

| ประเภทการ์ด | จำนวน | พฤติกรรม |
|---|---|---|
| **ปฏิเสธได้** (ฐานความยินยอม) | 5 | ยอมรับหรือปฏิเสธก็ได้ ไม่กระทบการใช้บริการ |
| **ปฏิเสธไม่ได้** (ฐานสัญญา/กฎหมาย) | 6 | กดได้แค่ "รับทราบ" + **แสดงเหตุผลเป็นภาษาชาวบ้านเสมอ** ว่าทำไมถึงปฏิเสธไม่ได้ |
| **แจ้งให้ทราบ** | 1 | เป็นการแจ้งข้อมูล ไม่ใช่การขอความยินยอม |

> ตัวอย่างเหตุผลที่แสดง: *"แอปส่งของต้องบอกที่อยู่คุณให้บริษัทขนส่ง ไม่งั้นของไปไม่ถึงบ้าน"* — ตรงข้ามกับ dark pattern ที่ทำให้ทุกอย่างดูเหมือนเลือกได้ทั้งที่จริงไม่ได้

**กลไกพิเศษ — การ์ดขูด (Scratch Card):**
2 ข้อที่มีความเสี่ยงซ่อนอยู่ (การโอนข้อมูลไปต่างประเทศ และการเก็บข้อมูล 10 ปี) ถูกปิดทับด้วยฟอยล์ทองแบบลอตเตอรี่ขูด ผู้ใช้ต้องขูดเองถึงจะเห็นคำวิเคราะห์ — เป็นจังหวะบังคับให้ "หยุดคิด" กับข้อที่คนมักอ่านผ่าน (มีปุ่มข้ามให้เสมอ ไม่บล็อกผู้ใช้)

**หน้าสรุปท้ายสุด:** สรุปทุกข้อว่ายอมรับ/ปฏิเสธ/รับทราบอะไรไปบ้าง — เป็นบันทึกความยินยอมที่ผู้ใช้เห็นได้

**ต้องมีอะไรถึงจะทำงานได้จริง:**
- ต้องแปลงประกาศความเป็นส่วนตัวของแต่ละองค์กรเป็นการ์ด (ปัจจุบันทำมือ 1 ฉบับ — ถ้าทำจริงอาจใช้ LLM ช่วยแตกข้อ + มนุษย์ตรวจ)
- ต้องมีที่เก็บบันทึกความยินยอมจริง (consent record) เพื่อใช้เป็นหลักฐานตามกฎหมาย

**คุณค่าที่ส่งมอบ:**
- ฝั่งผู้ใช้: รู้จริง ๆ ว่ากำลังยอมอะไร
- ฝั่งองค์กร: ได้ความยินยอมที่แยกเป็นรายวัตถุประสงค์ (granular consent) ซึ่งเป็นสิ่งที่กฎหมายต้องการ และได้หลักฐานว่าผู้ใช้ได้เห็นข้อความจริงก่อนตัดสินใจ (informed consent)

---

### ฟีเจอร์ 6 — การ์ดเกร็ดความรู้แบบเปิดทีละชั้น (Curiosity-Gap Cards)

**ทำอะไร:** ให้ความรู้เรื่องความเสี่ยงข้อมูลส่วนบุคคล ด้วยรูปแบบการเสพเนื้อหาแบบ TikTok/Duolingo

**กลไก:**
- แต่ละการ์ดเปิดด้วย "hook" ที่สร้างความสงสัย โดยดึงจุดเสี่ยงจริงจากประกาศความเป็นส่วนตัวมาเล่า
  > *"ลบแอปวันนี้ ข้อมูลการเงินของคุณยังอยู่กับเขาอีก **10 ปี**"*
  > *"รหัสผ่านหลุดยังเปลี่ยนได้ แต่**ใบหน้าของคุณ**เปลี่ยนไม่ได้ตลอดชีวิต"*
- แตะเพื่อเปิดคำตอบ **ทีละชั้น** ไม่เทข้อมูลทั้งหมดพร้อมกัน: เกิดอะไรขึ้น → ทำไมต้องสนใจ → ทำอะไรได้
- **ชั้นสุดท้ายคือข้อความจริงจากประกาศเสมอ** — ปิดท้ายด้วยหลักฐาน ไม่ใช่แค่คำบอกเล่า
- ปัจจุบันมี 5 การ์ด: ข้อมูลตำแหน่ง · การโอนข้อมูลต่างประเทศ · ข้อมูลชีวภาพ · การเก็บข้อมูล 10 ปี · คุกกี้

**ข้อแตกต่างจากฟีเจอร์ 5:** หน้านี้ให้ความรู้อย่างเดียว **ไม่มีปุ่มยอมรับ/ปฏิเสธ** ไม่ผูกกับการตัดสินใจใด ๆ

**ต้องมีอะไรถึงจะทำงานได้จริง:** เนื้อหาต้องเขียน/สร้างต่อเรื่อย ๆ เพื่อให้มีของใหม่ให้เสพ

**คุณค่าที่ส่งมอบ:** สร้างความตระหนักรู้ (awareness) โดยไม่ต้องบังคับให้อ่านเอกสารกฎหมาย — เป็นช่องทางดึงคนเข้าระบบและให้ความรู้ก่อนถึงจุดตัดสินใจ

## 3. ตารางสรุปความสามารถ

| ฟีเจอร์ | ประเภท | ใครได้ประโยชน์โดยตรง | ต้องพึ่งข้อมูล/ระบบภายนอกอะไร |
|---|---|---|---|
| 1. แดชบอร์ดความเสี่ยง | เครื่องมือผู้บริโภค | เจ้าของข้อมูล | แหล่งข้อมูลว่าใครถืออะไร |
| 2. คลังข้อมูล | เครื่องมือผู้บริโภค | เจ้าของข้อมูล | แหล่งข้อมูล + ROPA/data mapping |
| 3. เส้นทางข้อมูล + วิเคราะห์ + ปุ่มลบ | เครื่องมือผู้บริโภค + จุดเชื่อมองค์กร | เจ้าของข้อมูล | ROPA + ช่องทางรับคำขอขององค์กร + (LLM ถ้าทำวิเคราะห์อัตโนมัติ) |
| 4. ติดตามคำขอ (DSR Tracking) | จุดเชื่อมสองฝั่ง | เจ้าของข้อมูล **และ** องค์กร (audit trail) | ช่องทางรับ-ส่งสถานะกับองค์กร |
| 5. สาธิตการยินยอม | **ส่วนติดต่อที่องค์กรต้องมีตามกฎหมาย** | องค์กร (ได้ consent ที่ถูกต้อง) + เจ้าของข้อมูล | ประกาศความเป็นส่วนตัวขององค์กร + ที่เก็บ consent record |
| 6. เกร็ดความรู้ | เนื้อหา/การศึกษา | เจ้าของข้อมูล | คลังเนื้อหาที่ต้องผลิตต่อเนื่อง |

## 4. สถานะการพัฒนา — อะไรทำงานจริง อะไรจำลอง

### 4.1 ทำงานได้จริงแล้ว (ไม่ใช่ภาพนิ่ง)

- การปัดการ์ดด้วยนิ้วและเมาส์จริง พร้อมการตอบสนองระหว่างลาก
- การ์ดขูดที่ขูดได้จริง และตรวจว่าขูดไปกี่เปอร์เซ็นต์แล้วจริง
- การไล่สถานะคำขอตามเวลาจริง (เปิดทิ้งไว้แล้วเห็นสถานะขยับเอง)
- สถานะคงอยู่ข้ามหน้าและข้ามการรีเฟรช
- ตรรกะการคำนวณคะแนนความเสี่ยง การนับสถิติ และการกรองทั้งหมด
- ใช้งานผ่านคีย์บอร์ดได้ครบทุกฟังก์ชัน
- รองรับมือถือเต็มรูปแบบ
- Deploy ได้ทันที (build เป็นไฟล์สแตติก 22 หน้า)

### 4.2 จำลองไว้ (ต้องต่อของจริงถ้าจะใช้งานจริง)

| ส่วน | สถานะปัจจุบัน | ถ้าทำจริงต้องมี |
|---|---|---|
| **ข้อมูลว่าใครถืออะไร** | ข้อมูลสมมติคงที่: 8 องค์กร 13 รายการข้อมูล | เชื่อมแหล่งข้อมูลจริง เช่น ระบบขององค์กรเอง, การสแกนอีเมล, consent registry |
| **บทวิเคราะห์ความเสี่ยง** | ข้อความเขียนไว้ล่วงหน้าทั้งหมด | เรียก LLM สร้างต่อรายการ (โครงสร้างรองรับแล้ว เปลี่ยนแค่แหล่งข้อความ) |
| **การส่งคำขอลบ (DSR API)** | จำลองด้วยตัวจับเวลาในเครื่องผู้ใช้ | ต่อกับช่องทางจริงขององค์กร — API มาตรฐาน, อีเมล DPO, หรือระบบ DSR ที่มีอยู่ |
| **การยืนยันตัวตน** | ไม่มีเลย | จำเป็นมาก — ต้องพิสูจน์ว่าคนกดขอลบคือเจ้าของข้อมูลจริง ไม่งั้นใครก็สั่งลบข้อมูลคนอื่นได้ |
| **ข้อมูลข้ามอุปกรณ์** | เก็บในเครื่องเดียว (localStorage) | ต้องมี backend + ระบบบัญชีผู้ใช้ |
| **บันทึกความยินยอม** | เก็บในเครื่องผู้ใช้ ไม่ใช่หลักฐานทางกฎหมาย | ต้องมีที่เก็บฝั่งเซิร์ฟเวอร์ที่แก้ไขย้อนหลังไม่ได้ |
| **การแยกประเภทคุกกี้** | รวมเป็นก้อนเดียว (ตามที่ประกาศต้นฉบับเขียนไว้) | แยกตามมาตรฐาน IAB/TCF (necessary / analytics / marketing) |

## 5. ข้อมูลตัวอย่างที่ใช้ในต้นแบบ

> ทั้งหมดเป็นข้อมูลสมมติ ไม่มีบริษัทจริง

**8 องค์กรผู้ถือข้อมูล** ครอบคลุมหลายอุตสาหกรรมโดยตั้งใจ:
อีคอมเมิร์ซ · แอปสินเชื่อออนไลน์ · ฟู้ดเดลิเวอรี่ · ฟิตเนส (สมาชิกหมดอายุแล้ว) · ซูเปอร์มาร์เก็ต · **นายหน้าข้อมูล (Data Broker)** · ค่ายมือถือเก่า (เลิกใช้ 3 ปี) · โรงแรม

**13 รายการข้อมูล** แบ่งเป็นเสี่ยงสูง 6 · ปานกลาง 4 · ต่ำ 3 โดยระบบแนะนำให้ลบ 5 รายการ

**สถานการณ์ที่จงใจออกแบบให้เห็นภาพ:**
- ข้อมูลไหลจากหลายองค์กรไปรวมที่นายหน้าข้อมูลรายเดียว (แสดงว่าทำไมต้องตัดที่ต้นทาง)
- องค์กรที่เลิกใช้บริการไปแล้วแต่ยังถือข้อมูลอยู่ (ยิม, ค่ายมือถือ)
- ข้อมูลอ่อนไหวตามกฎหมาย (สุขภาพ, ชีวภาพ) แยกออกจากข้อมูลทั่วไป
- แอปที่เก็บข้อมูลเกินความจำเป็น (แอปกู้เงินดูดรายชื่อผู้ติดต่อทั้งเครื่อง)

## 6. ความสอดคล้องกับสิทธิ์ตาม PDPA

| สิทธิ์ตามกฎหมาย | ฟีเจอร์ที่รองรับ |
|---|---|
| สิทธิ์ในการเข้าถึงข้อมูล (Right to Access) | ฟีเจอร์ 1, 2, 3 |
| **สิทธิ์ในการลบข้อมูล (Right to Erasure)** | **ฟีเจอร์ 3, 4 — เป็นฟีเจอร์แกนของผลิตภัณฑ์** |
| สิทธิ์ในการถอนความยินยอม (Right to Withdraw Consent) | ฟีเจอร์ 5 |
| สิทธิ์ในการคัดค้านการประมวลผล (Right to Object) | ฟีเจอร์ 5 (การ์ดที่เปิดให้ปฏิเสธเกินกว่าที่กฎหมายบังคับ) |
| หน้าที่แจ้งข้อมูลให้โปร่งใส (Transparency) | ฟีเจอร์ 3 (Data Trail), 5, 6 |
| กรอบเวลาตอบคำขอ 30 วัน | ฟีเจอร์ 4 (แถบ SLA) |

**สิทธิ์ที่ยังไม่ได้ทำ:** สิทธิ์ในการแก้ไขข้อมูล · สิทธิ์ในการโอนย้ายข้อมูล · สิทธิ์ในการระงับการใช้ · สิทธิ์ในการร้องเรียนต่อ สคส.

## 7. สิ่งที่ระบบยังไม่มี (ช่องว่างที่รู้ตัว)

- ไม่มีหน้าจอหรือเครื่องมือใด ๆ **สำหรับฝั่งองค์กร** — ไม่มี admin console, ไม่มี dashboard ให้ DPO ดูคำขอที่เข้ามา, ไม่มีระบบจัดการ ROPA
- ไม่มีการรายงาน/สถิติเชิงองค์กร (เช่น องค์กรตอบคำขอทันกรอบเวลากี่ %)
- ไม่มีระบบแจ้งเตือน (notification / email)
- ไม่มีระบบคิดเงินหรือจัดการบัญชีผู้ใช้
- ไม่รองรับหลายภาษา (ไทยอย่างเดียว)
- ยังไม่ได้ทำเป็น SDK / embeddable widget / white-label
